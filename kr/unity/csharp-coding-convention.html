핵심 규칙

01

세미콜론 문장과 함수 선언·호출을 임의로 줄바꿈하지 않는다

올바른 사용
ApplyReward(item, count);
잘못된 사용
ApplyReward(
    item, count);

새로 쓰거나 수정하는 문장, 함수 선언부와 호출 인수는 길이와 관계없이 한 줄로 쓴다. 기존 수동 줄바꿈은 요청 없이 바꾸지 않는다.

02

단일 내장문 본문은 중괄호 생략을 강력히 권장한다

올바른 사용
if (ready)
    Start();
잘못된 사용
if (ready)
{
    Start();
}

단일문은 중괄호를 생략한다. 제어문 하나를 감싸는 제어문은 else if를 제외하고 바깥쪽에 중괄호를 쓴다. 같은 if 연쇄는 중괄호 사용을 통일한다.

03

Attribute는 한 줄에 하나씩 명시한다

Attribute는 선언 바로 위에 한 줄에 하나씩 쓴다.

04

빈 줄은 정확히 한 줄의 완전히 빈 줄로 쓴다

필요한 경계와 using 뒤에는 완전히 빈 줄 하나만 둔다. 연속 빈 줄, 공백이 든 빈 줄, 중괄호 바로 안쪽 빈 줄은 금지한다.

05

타입 범위의 그룹은 빈 줄로 구분한다

타입 범위의 멤버 섹션, 상속 그룹, 중첩 타입, 함수 사이는 한 줄 띄운다. 같은 그룹과 선언에 붙는 메타데이터는 분리하지 않는다.

06

블록 안에서는 논리 문단 사이에만 빈 줄을 둔다

블록에서는 목적이 다른 완결된 문장 그룹 사이만 한 줄 띄운다. 값은 즉시 검증·소비와 붙이고 else나 닫는 중괄호 앞은 띄우지 않는다.

07

Unity 객체에는 null 조건부·병합 연산자를 쓰지 않는다

올바른 사용
if (target != null)
    target.Reset();
잘못된 사용
target?.Reset();

UnityEngine.Object에는 ?., ??, ??=를 쓰지 말고 Unity null 검사와 명시적 fallback을 쓴다. 가려진 Unity 객체는 복원해 검사한다. 일반 관리 객체, nullable, 삼항식, delegate와 event는 제외한다.

08

인터페이스는 Interface 접미사를 쓴다

인터페이스 타입에만 Interface 접미사를 쓴다.

09

static 필드의 밑줄 수는 직접 선언한 타입으로 정한다

올바른 사용
public static int __Count;
private static int __count;
잘못된 사용
public static int _Count;
private static int _count;

const·readonly 외 static 필드는 일반 타입에서 public __PascalCase/private __camelCase, static class에서 public _PascalCase/private _camelCase를 쓴다. 직접 선언한 타입으로 판단한다.

10

const와 readonly는 PascalCase를 쓴다

const와 readonly는 접두 밑줄 없는 PascalCase를 쓴다. 변경 가능한 static readonly 객체는 31번도 따른다.

11

속성은 명사 또는 형용사로 쓴다

속성은 명사·형용사로 짓고 Boolean 질문은 동작명 대신 Is·Has를 쓴다.

12

Can과 -able의 의미를 구분한다

CanX는 실행 능력, Xable은 속성을 뜻한다.

13

검색성이 중요한 속성에는 타입 postfix를 붙인다

String, Sprite, Prefab, Effect, Tooltip 같은 속성 타입 접미사는 검색성이 좋아질 때만 쓴다.

14

함수는 동사 또는 동사구로 쓴다

15

Enum 타입은 Enum 접미사를 쓴다

enum 타입에는 Enum 접미사를 붙이고 변수명에는 반복하지 않는다.

16

코루틴 함수는 Coroutine 접미사를 쓴다

17

파일명과 대표 정의명을 맞춘다

18

파일 1개에는 대표 정의 1개만 둔다

파일 하나에는 대표 최상위 class·struct·enum 하나만 둔다. 중첩 타입은 제외한다.

19

중첩 타입은 enum, struct, interface, class 순서로 둔다

20

파일명과 클래스명은 명사로 둔다

파일·클래스는 역할 명사로 짓고 동작은 함수명에 둔다.

21

Unity 객체 이름과 스크립트 이름을 맞춘다

SECTION

22

PascalCase 경계는 의미 계층을 나타낸다

프로젝트 비즈니스 로직의 PascalCase는 실제 소유·구조·관계·역할 계층만 나눈다. 엔진·라이브러리·저수준 코드는 제외한다.

23

다른 키워드의 부분 문자열이면 피한다

24

복수 그룹은 현재 -s/-es를 허용한다

그룹은 -s·-es 복수형을 쓰고 List·Array·Bucket 같은 타입 소음 접미사는 피한다.

구문과 구성

25

외부 생명주기 객체는 읽기 전용 속성으로 둔다

26

객체 생성에서 타입을 중복 기재하지 않는다

올바른 사용
Item item = new();
잘못된 사용
Item item = new Item();

생성 타입을 반복하지 않는다. 생성식에 타입이 있으면 var, 대상에 타입이 있으면 new(...)·new()를 쓴다.

27

신규 using 형태는 사용하지 않는다

28

sealed는 override 앞에 둔다

29

클래스 내부 섹션은 변수, 속성, 이벤트, 함수 순서로 둔다

class 섹션은 중첩 타입 > 변수 > 속성 > 이벤트 > 함수 순서로 둔다.

30

각 카테고리 내부는 abc순으로 둔다

29·31·34번을 먼저 적용하고 같은 category·상속 그룹 안에서만 이름순으로 정렬한다.

31

변수·속성·함수는 static, 상속 구현, 자기 것 순서로 둔다

올바른 사용
private static void ResetAll() { }
protected override void Refresh() { }
private void Run() { }
잘못된 사용
private void Run() { }
protected override void Refresh() { }
private static void ResetAll() { }

그룹은 static > 상속 구현 > 자기 것 순서이며 생성자·소멸자는 함수 그룹보다 앞선다. 지원 field·property는 해당 상속 그룹에 둔다. MonoBehaviour는 Unity 메시지(이름순) > 부모(선언순) > interface(이름순) > 자기 것 순서다. static은 타입 소유일 때만 쓰고 생명주기·reset·cleanup·동시성을 정한다.

32

불필요한 함수를 만들지 않는다

재사용, 독립 책임·계약, 명확한 문맥 경계가 있을 때만 함수를 추출한다. framework 진입점·override·명시적 interface·callback은 제외한다. local 함수는 호출자 안 재사용, 종속 coroutine, 긴 접기 블록에만 쓴다.

33

인터페이스 구현은 타입 explicit으로 둔다

interface는 InterfaceName.MemberName 형태로 명시적으로 구현한다.

34

멤버 변수 섹션은 const, readonly, static, member 순서로 둔다

변수는 const > readonly > static > 상속 구현 > 자기 것 순서이며 같은 상속 그룹 안에서만 이름순으로 정렬한다.

35

증감 연산자는 전위형으로 쓴다

36

논리 부정 연산자는 Boolean 토글 대입에만 쓴다

!는 Boolean 값을 뒤집어 다시 대입할 때만 쓰고 그 외에는 false와 비교한다.

37

접근 제한자에 따라 멤버를 정렬하지 않는다

접근 제한자로 멤버를 묶거나 정렬하지 않고 29~31번과 34번을 따른다.

38

비교식은 괄호로 감싸되 완결된 단일 항목은 감싸지 않는다

올바른 사용
if ((count > 0) && ready)
잘못된 사용
if (count > 0 && (ready))

논리식에서는 비교식과 중첩 복합식에 괄호를 쓰고 독립된 Boolean 항목에는 쓰지 않는다.

39

올바른 케이스와 주요 관심 분기를 먼저 둔다

40

로그 작성 지침을 따른다

41

한 번만 쓰는 값은 지역 변수로 이름 붙이지 않는다

한 번만 쓰는 값은 인라인한다. 두 번 이상 쓰거나 문법·실행 의미상 저장이 필요할 때만 지역 변수를 둔다.

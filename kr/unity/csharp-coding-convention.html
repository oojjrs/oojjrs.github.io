Unity C# 코딩 컨벤션

Home
목적
  • 코드 모양을 고민하는 시간을 0에 가깝게 줄인다.
  • 도메인 숙련도가 높아질수록 코드 분석 속도가 0에 가까워지게 한다.
수단
  • IDE와 표준 도구의 기본 규칙을 최대한 그대로 쓴다.
  • 수동 코딩 중 판단 기준을 단순하게 유지한다.
  • 동사-함수, 명사-변수처럼 컨텍스트 정보를 일관되게 둔다.
  • 최종 검수와 수동 코딩 기준을 맞추기 위해 AI에게도 동일하게 요구한다.
서드파티 코드 영역은 이 컨벤션 적용 대상이 아니다. 기존 도메인이 존재하는 곳은 항상 기존 원칙을 우선한다.
적용 우선순위
  1. 이 문서
  2. Unity C# Style
  3. Visual Studio Code Style 기본 옵션 / C# Coding Conventions

이 문서에서 언급하지 않은 컨벤션은 Unity 기준과 Visual Studio Code Style 기본 옵션을 따른다.

07

Unity 객체에는 null 조건부·병합 연산자를 쓰지 않는다

올바른 사용
private void ResetTarget(Transform target)
{
    if (target != null)
        target.SetPositionAndRotation(Vector3.zero, Quaternion.identity);
}

private Transform SelectTarget(Transform target, Transform fallback)
{
    if (target != null)
        return target;

    return fallback;
}

private void SetTargetFallback(Transform fallback)
{
    if (_target == null)
        _target = fallback;
}
잘못된 사용
private void ResetTarget(Transform target)
{
    target?.SetPositionAndRotation(Vector3.zero, Quaternion.identity);
}

private Transform SelectTarget(Transform target, Transform fallback)
{
    return target ?? fallback;
}

private void SetTargetFallback(Transform fallback)
{
    _target ??= fallback;
}

09

static 필드만 직접 선언한 타입에 따라 접두사를 정한다

판정 순서는 (1) 필드 선언 자체에 static이 있는지, (2) 그 필드를 직접 선언한 타입이 static인지다. 필드 선언에 static이 없으면 9번을 적용하지 않고, const는 10번을 따른다. 이 관문을 통과한 static 필드는 비정적 타입에 직접 선언되면 public __PascalCase/private __camelCase, static class에 직접 선언되면 public _PascalCase/private _camelCase를 쓴다. 중첩 타입에서는 바깥 타입을 보지 않는다.

이름 규칙상 올바른 사용
public sealed class Cache
{
    public static int __Capacity;
    private static int __index;

    private int _index;
}

public static class CacheRegistry
{
    public static int _Capacity;
    private static int _index;
}
이름 규칙상 잘못된 사용
public sealed class Cache
{
    public static int _Capacity;
    private static int _index;

    private int __index;
}

public static class CacheRegistry
{
    public static int __Capacity;
    private static int __index;
}

10번에 따라 const와 상수 역할의 static readonly는 이 접두사를 쓰지 않는다. 그 밖의 static readonly는 모두 이 접두사를 따른다.

10

const와 상수 역할의 static readonly만 PascalCase를 쓴다

올바른 사용
private const int MaxCount = 10;
private static readonly TimeSpan RetryDelay = TimeSpan.FromSeconds(3);
private static readonly Guid ProtocolId = new("b70f0f2a-9a5d-4f97-8631-b1eb495a01d3");
private static readonly Guid __sessionId = Guid.NewGuid();
private static readonly List<Item> __items = new();
private readonly int _startIndex;
잘못된 사용
private static readonly TimeSpan __retryDelay = TimeSpan.FromSeconds(3);
private static readonly Guid SessionId = Guid.NewGuid();
private static readonly List<Item> Items = new();
private readonly int StartIndex;

static readonly는 실행 상태의 스냅샷이나 소유 객체가 아니라 프로그램 또는 API의 정의값을 나타낼 때만 상수 역할로 본다. 초기화 뒤 의미값과 그 의미에 참여하는 도달 가능한 관찰 상태가 바뀔 수 없어야 하며, 참조 동일성, 수명, 동기화, 지연 생성, 서비스 또는 캐시 상태가 의미에 관여해서는 안 된다.

시간, 난수, 환경, 설정, I/O, Unity 오브젝트에서 얻은 실행값과 현재 코드가 우연히 변경하지 않을 뿐인 가변 객체는 상수 역할이 아니다. 인스턴스 readonly와 그 밖의 readonly는 일반 필드 명명을 따른다. private 인스턴스는 _camelCase, static은 9번 접두사를 쓰며, 애매하면 일반 필드명으로 분류한다. 이 구분은 이름에만 적용하고 배치 순서는 34번을 따른다. 변경 가능한 static 상태에는 31번도 적용한다.

27

using var 선언은 쓰지 않고, 한 줄 단순문 본문은 중괄호를 생략하며 그 밖에는 쓴다

using (...) 본문이 세미콜론으로 끝나는 한 줄 단순문 하나면 중괄호를 생략하고, 그 밖의 본문에는 중괄호를 쓴다. using이 중첩되면 다른 using을 본문으로 갖는 바깥 using에는 중괄호를 쓰고, 가장 안쪽 using의 본문이 한 줄 단순문이면 중괄호를 생략한다.

올바른 사용
using (var stream = File.OpenRead(path))
    Process(stream);

using (var input = File.OpenRead(sourcePath))
{
    using (var output = File.Create(destinationPath))
        input.CopyTo(output);
}
잘못된 사용
using var stream = File.OpenRead(path);

using (var input = File.OpenRead(sourcePath))
using (var output = File.Create(destinationPath))
{
    input.CopyTo(output);
}

using (var input = File.OpenRead(sourcePath))
{
    using (var output = File.Create(destinationPath))
    {
        input.CopyTo(output);
    }
}

internal은 사용자가 명시적으로 지정한 경우에만 쓴다

명시적 internal 제한자, protected internal처럼 internal을 포함한 복합 접근 제한자, 접근 제한자를 생략해 암시적으로 internal이 되는 최상위 타입을 모두 금지한다. 어셈블리 경계, 패키지 구현 세부, 테스트 노출, 인접 코드만으로 internal을 추론하지 않는다. 사용자가 특정 선언이나 범위를 internal로 명시적으로 지정한 경우에만 그 지정 범위에 쓸 수 있다. 그 밖에는 의도한 API 공개 범위에 맞는 internal 이외의 접근 제한자를 명시한다.

사용자가 internal을 지정하지 않았을 때 올바른 사용
public sealed class RewardCatalog
{
    private sealed class Entry
    {
    }
}
사용자의 명시적 지정이 없을 때 잘못된 사용
sealed class RewardCatalog
{
    internal sealed class Entry
    {
    }
}

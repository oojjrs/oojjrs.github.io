Unity C# 코딩 컨벤션

Home
목적
  • 코드 모양을 고민하는 시간을 0에 가깝게 줄인다.
  • 도메인 숙련도가 높아질수록 코드 분석 속도가 0에 가까워지게 한다.
수단
  • IDE와 표준 도구의 기본 규칙을 최대한 그대로 쓴다.
  • 수동 코딩 중 판단 기준을 단순하게 유지한다.
  • 동사-함수, 명사-변수처럼 컨텍스트 정보를 일관되게 둔다.
  • 최종 검수와 수동 코딩 기준을 맞추기 위해 AI에게도 동일하게 요구한다.
서드파티 코드 영역은 이 컨벤션 적용 대상이 아니다. 기존 도메인이 존재하는 곳은 항상 기존 원칙을 우선한다.

관련 필수 지침

로그를 추가하거나 수정할 때는 종류, 대문자 문구, identifier 참조, 안정성 규칙을 정한 로그 작성 지침을 함께 따른다.

명명파일과 Unity 객체단어구문과 구성
SECTION

명명

01

인터페이스는 Interface 접미사를 쓴다

올바른 사용
public interface FunctionInterface
{
}

private FunctionInterface function;
잘못된 사용
public interface IFunction
{
}

private FunctionInterface functionInterface;

Interface 표시는 타입명에만 둔다.

02

static 멤버 변수는 밑줄 2개를 붙인다

올바른 사용
public static int __Index;
private static int __index;
잘못된 사용
public static int Index;
private static int _index;
private static int index;

public static은 __PascalCase, private static은 __camelCase로 둔다.

03

const와 readonly는 PascalCase를 쓴다

올바른 사용
private const int MaxCount = 10;
private readonly int StartIndex;
잘못된 사용
private const int max_count = 10;
private readonly int start_index;

상수형 멤버도 타입/속성 이름처럼 읽히게 한다.

04

속성은 명사 또는 형용사로 쓴다

올바른 사용
public bool IsActive { get; }
public bool HasReward { get; }
public Item AsItem { get; }
잘못된 사용
public bool Active { get; }
public bool Activate { get; }
public bool Reward { get; }

묻는 형태의 bool 속성은 Is, Has 같은 접두사로 IDE 검색을 모은다.

05

Can과 -able의 의미를 구분한다

올바른 사용
public bool CanGather { get; }
public bool Gatherable { get; }
잘못된 사용
public bool CanGathered { get; }
public bool Gather { get; }

CanGather는 객체가 하는 행위, Gatherable은 객체가 가진 속성이다.

06

검색성이 중요한 속성에는 타입 postfix를 붙인다

올바른 사용
public Sprite IconSprite { get; }
public GameObject HitEffect { get; }
public string DescriptionTooltip { get; }
잘못된 사용
public Sprite Icon { get; }
public GameObject Hit { get; }
public string Description { get; }

String, Sprite, Prefab, Effect, Tooltip처럼 검색 필터가 필요한 경우만 쓴다.

07

함수는 동사 또는 동사구로 쓴다

올바른 사용
public void GiveReward()
{
}
잘못된 사용
public void Reward()
{
}

동작은 함수명에서 바로 드러나야 한다.

08

Enum 타입은 Enum 접미사를 쓴다

올바른 사용
public enum ItemGroupEnum
{
}

private ItemGroupEnum itemGroup;
잘못된 사용
public enum ItemGroup
{
}

private ItemGroup itemGroupEnum;

변수명에는 Enum을 반복하지 않는다.

09

코루틴 함수는 Coroutine 접미사를 쓴다

올바른 사용
private IEnumerator FadeCoroutine()
{
    yield return null;
}
잘못된 사용
private IEnumerator Fade()
{
    yield return null;
}

실행 방식이 다른 함수를 이름에서 구분한다.

SECTION

파일과 Unity 객체

10

파일명과 대표 정의명을 맞춘다

올바른 사용
// File: PlayerController.cs
public sealed class PlayerController
{
}
잘못된 사용
// File: Player.cs
public sealed class PlayerController
{
}

IDE와 IntelliSense에서 파일과 타입을 바로 찾을 수 있어야 한다.

11

파일 1개에는 대표 정의 1개만 둔다

올바른 사용
// File: PlayerController.cs
public sealed class PlayerController
{
    private enum StateEnum
    {
    }
}
잘못된 사용
// File: PlayerController.cs
public sealed class PlayerController
{
}

public struct PlayerState
{
}

public enum PlayerModeEnum
{
}

class, struct, enum 등 대표 정의는 파일을 나눈다. 중첩 정의는 예외다.

12

중첩 타입은 enum, struct, interface, class 순서로 둔다

올바른 사용
public sealed class PlayerController
{
    private enum StateEnum
    {
    }

    private struct Entry
    {
    }

    private interface CacheInterface
    {
    }

    private sealed class Cache
    {
    }
}
잘못된 사용
public sealed class PlayerController
{
    private sealed class Cache
    {
    }

    private interface CacheInterface
    {
    }

    private enum StateEnum
    {
    }

    private struct Entry
    {
    }
}

한 파일의 여러 타입 선언은 대표 정의 1개 원칙 때문에 보통 중첩 타입에만 허용한다. 중첩 타입 선언 순서는 enum > struct > interface > class다.

13

파일명과 클래스명은 명사로 둔다

올바른 사용
// File: PlayerMover.cs
public sealed class PlayerMover
{
}
잘못된 사용
// File: MovePlayer.cs
public sealed class MovePlayer
{
}

역할은 타입명에, 동작은 함수명에 둔다.

14

Unity 객체 이름과 스크립트 이름을 맞춘다

올바른 사용
Prefab: InventoryPanel
Script: InventoryPanel.cs
Class: InventoryPanel
잘못된 사용
Prefab: Inventory
Script: BagPanel.cs
Class: BagPanel

Inspector 이름과 코드 검색 이름이 같은 개념을 가리켜야 한다.

SECTION

단어

15

PascalCase 경계는 의미 계층을 나타낸다

올바른 사용
Nickname
TitleMenuButton
LobbyRoomListEntryHostText
잘못된 사용
NickName
TitlemenuButton
LifeTime

한 의미 계층은 한 토큰으로 쓴다. 새 대문자 경계는 철자를 끊는 표시가 아니라 실제 소유·구조·관계·역할 계층을 하나 추가한다는 선언이다. Nickname은 한 개념이고, TitleMenuButton은 실제 Title → Menu → Button 구조다. 사전이 아니라 코드 구조로 경계를 판정한다. 자세한 기준은 의미 계층 기반 네이밍에서 다룬다.

16

다른 키워드의 부분 문자열이면 피한다

올바른 사용
StageState
IntermissionState
잘못된 사용
MissionState
IntermissionState

Intermission 안에 Mission이 들어간다. 검색하면 Mission이 의도치 않게 같이 잡힌다.

17

복수 그룹은 현재 -s/-es를 허용한다

올바른 사용
Items
Enemies
Rewards
잘못된 사용
ItemList
EnemyArray
RewardBucket

List, Array는 헝가리언처럼 보일 수 있다. 더 나은 대안은 미정이다.

SECTION

구문과 구성

18

외부 생명주기 객체는 읽기 전용 속성으로 둔다

올바른 사용
public Player Player { get; }
잘못된 사용
public Player Player;

생성과 소유권이 외부에 있으면 setter를 닫는다.

19

객체 생성에서 타입을 중복 기재하지 않는다

올바른 사용
public sealed class Inventory
{
    private Dictionary<string, Item> items =
        new(StringComparer.Ordinal);

    public List<Item> Items { get; } = new();

    private void Refresh()
    {
        var rewards = new List<Reward>();
    }
}
잘못된 사용
public sealed class Inventory
{
    private Dictionary<string, Item> items =
        new Dictionary<string, Item>(StringComparer.Ordinal);

    public List<Item> Items { get; } = new List<Item>();

    private void Refresh()
    {
        List<Reward> rewards = new List<Reward>();
    }
}

지역 변수는 오른쪽 생성식에 타입이 명시되어 있으면 var를 쓴다. 선언부나 대입 대상에 타입이 이미 명시되어 있으면, 특히 클래스 멤버 변수와 속성에서는 target-typed new(arguments) 또는 new()를 쓴다. 같은 생성 타입을 양쪽에 반복하지 않는다.

20

신규 using 형태는 사용하지 않는다

올바른 사용
using (var stream = File.OpenRead(path))
{
}
잘못된 사용
using var stream = File.OpenRead(path);

기존 using 블록 형태를 유지한다.

21

sealed는 override 앞에 둔다

올바른 사용
public sealed override void Dispose()
{
}
잘못된 사용
public override sealed void Dispose()
{
}

접근 제한자, sealed, override 순서로 읽히게 한다.

22

클래스 내부 섹션은 변수, 속성, 이벤트, 함수 순서로 둔다

올바른 사용
private enum StateEnum { }
private struct Entry { }
private interface CacheInterface { }
private sealed class Cache { }
private const int MaxCount = 10;
public int Count { get; }
public event Action Changed;
public void Refresh() { }
잘못된 사용
public void Refresh() { }
public int Count { get; }
private enum StateEnum { }

inner enum, inner struct, inner interface, inner class 다음은 변수 > 속성 > 이벤트 > 함수 순서다.

23

각 카테고리 내부는 abc순으로 둔다

올바른 사용
private int alphaCount;
private int betaCount;
private int rewardCount;

public bool IsActive { get; }
public int RewardCount { get; }
public string TooltipText { get; }

public event Action Changed;
public event Action Selected;

public void ApplyReward()
{
}

public void RefreshTooltip()
{
}
잘못된 사용
private int rewardCount;
private int alphaCount;
public void ApplyReward()
{
}
public bool IsActive { get; }
public event Action Selected;
public string TooltipText { get; }
public event Action Changed;
public void RefreshTooltip()
{
}

abc 정렬은 섹션 순서와 공통 멤버 순서를 먼저 적용한 뒤 같은 상속 그룹의 같은 카테고리 내부에서만 적용한다. 변수는 const > readonly > static > 상속 구현 > 자기 인스턴스 멤버, 속성은 static > 상속 구현 > 자기 인스턴스 멤버, 함수는 생성자·소멸자 > static > 상속 구현 > 자기 인스턴스 함수 순서다. abc 정렬 때문에 부모/인터페이스 구현 그룹을 섞지 않는다.

24

변수·속성·함수는 static, 상속 구현, 자기 것 순서로 둔다

올바른 사용
public sealed class RewardButton : ButtonBase, ClickableInterface, TooltipInterface
{
    private static int __rewardTypeCount;

    private int buttonIndex;
    private int clickableCount;
    private int tooltipCount;
    private int rewardCount;

    public static int RewardTypeCount { get; }

    public bool IsButtonActive { get; }
    public bool IsClickable { get; }
    public string TooltipText { get; }
    public int RewardCount { get; }

    private static void RegisterRewardType()
    {
    }

    private void Awake()
    {
    }

    private void OnDestroy()
    {
    }

    private void OnEnable()
    {
    }

    private void Start()
    {
    }

    protected override void RefreshButton()
    {
    }

    void ClickableInterface.Click()
    {
    }

    void TooltipInterface.ShowTooltip()
    {
    }

    public void GiveReward()
    {
    }
}
잘못된 사용
public sealed class RewardButton : ButtonBase, TooltipInterface, ClickableInterface
{
    private int rewardCount;
    private static int __rewardTypeCount;
    private int tooltipCount;
    private int buttonIndex;

    public int RewardCount { get; }
    public static int RewardTypeCount { get; }
    public string TooltipText { get; }

    public void GiveReward()
    {
    }

    private static void RegisterRewardType()
    {
    }

    public void ShowTooltip()
    {
    }

    private void Awake()
    {
    }

    protected override void RefreshButton()
    {
    }
}

변수, 속성, 함수는 각 카테고리 안에서 static 멤버 > 상속 구현 멤버 > 자기 인스턴스 멤버 순서로 둔다. 함수에서는 생성자와 소멸자를 이 순서보다 먼저 두고, 변수에서는 const와 readonly를 먼저 둔다. 상속 구현을 지원하는 변수와 속성도 해당 부모 또는 인터페이스의 상속 그룹에 포함한다. static, 상속 구현, 자기 것 그룹을 섞지 않는다. static 클래스가 아닌 일반 객체에서는 동작이 타입 자체의 책임인 경우가 아니면 static 함수를 가급적 사용하지 않는다. MonoBehaviour에서는 Unity 메시지 함수를 암시적으로 가장 먼저 상속받은 그룹처럼 취급한다. 명시적으로 상속받은 부모와 인터페이스 멤버보다 먼저 두고, Awake, OnDestroy, OnEnable, Start처럼 함수명 abc순으로 정렬한다. Unity 생명주기 순서로 정렬하지 않는다. 그 뒤에는 부모 > 자식 순서를 적용한다. 명시적 부모 간에는 상속 선언 순서를 따르고, 여러 인터페이스의 선언과 구현은 abc순으로 둔다.

25

불필요한 함수를 만들지 않는다

올바른 사용
private void ApplyReward()
{
    rewardCount += bonusCount;
    RefreshTooltip();
}
잘못된 사용
private void AddBonus()
{
    rewardCount += bonusCount;
}

private void ApplyReward()
{
    AddBonus();
    RefreshTooltip();
}

재사용, 독립된 책임이나 계약, 더 명확한 문맥 경계가 생기지 않는 일회성 로직은 호출부에 둔다. Unity 메시지, override, 명시적 인터페이스 구현, 등록된 콜백, 프레임워크 진입점은 예외다. 지역 함수는 상위 함수 내부 재사용, 종속 코루틴, 접어 둘 만큼 긴 블록에만 쓴다.

26

인터페이스 구현은 타입 explicit으로 둔다

올바른 사용
public sealed class TooltipButton : TooltipInterface
{
    string TooltipInterface.TooltipText => tooltipText;

    void TooltipInterface.ShowTooltip()
    {
    }
}
잘못된 사용
public sealed class TooltipButton : TooltipInterface
{
    public string TooltipText => tooltipText;

    public void ShowTooltip()
    {
    }
}
27

멤버 변수 섹션은 const, readonly, static, member 순서로 둔다

올바른 사용
private const int MaxCount = 10;

private readonly int StartIndex;

private static int __cacheCount;
private static int __index;

private int count;
private int index;
잘못된 사용
private const int MaxCount = 10;
private int index;
private readonly int StartIndex;
private static int __cacheCount;
private int count;

const, readonly, static, 일반 변수는 별도 섹션으로 두고, 일반 변수는 24번 순서에 따라 같은 상속 그룹 안에서만 이름순으로 정렬한다.

28

단일 내장문 본문은 중괄호 생략을 강력히 권장한다

올바른 사용
if (isReady)
    StartGame();

foreach (var enemy in enemies)
    enemy.Update();

foreach (var index in Indexes)
{
    if (index.CanAdd(entity, primaryKey) == false)
        return false;
}

if (isReady)
{
    StartGame();
}
else if (canRetry)
{
    ResetGame();
    RetryGame();
}
else
{
    CancelGame();
}
명확한 사유가 없다면 잘못된 사용
foreach (var enemy in enemies)
{
    enemy.Update();
}

foreach (var index in Indexes)
    if (index.CanAdd(entity, primaryKey) == false)
        return false;

단일 내장문 본문은 명확한 이유가 있을 때만 중괄호를 유지한다. 다만 중괄호 없는 제어문을 연속으로 중첩하지 않는다. else if 연쇄를 제외하고, 제어문의 유일한 본문이 다른 제어문이면 바깥 본문에 중괄호를 쓰고 가장 안쪽의 단일 실행문에서만 생략한다. 같은 if 연쇄에서 한 분기라도 중괄호가 필요하면 모든 분기에 쓴다.

29

증감 연산자는 전위형으로 쓴다

올바른 사용
++index;
--index;
잘못된 사용
index++;
index--;
30

논리 부정 연산자는 Boolean 토글 대입에만 쓴다

올바른 사용
isActive = !isActive;

if (isActive == false)
    Activate();
잘못된 사용
if (!isActive)
    Activate();

return !isActive;

!는 같은 Boolean 변수의 토글 대입에만 사용하고, 그 밖에는 == false로 비교한다.

31

접근 제한자에 따라 멤버를 정렬하지 않는다

올바른 사용
public int AlphaCount { get; }
private int BetaCount { get; }
protected int EnemyCount { get; }
private int ItemCount { get; }
public int RewardCount { get; }
protected int StageCount { get; }
잘못된 사용
public int AlphaCount { get; }
public int RewardCount { get; }
protected int EnemyCount { get; }
protected int StageCount { get; }
private int BetaCount { get; }
private int ItemCount { get; }

접근 제한자는 멤버 순서에 영향을 주지 않는다. 22~24번과 27번을 따른다.

41

Unity 객체에는 null 조건부·병합 연산자를 쓰지 않는다

올바른 사용
private void ResetTarget(Transform target)
{
    if (target != null)
        target.SetPositionAndRotation(Vector3.zero, Quaternion.identity);
}

private Transform SelectTarget(Transform target, Transform fallback)
{
    if (target != null)
        return target;

    return fallback;
}

private void SetTargetFallback(Transform fallback)
{
    if (_target == null)
        _target = fallback;
}
잘못된 사용
private void ResetTarget(Transform target)
{
    target?.SetPositionAndRotation(Vector3.zero, Quaternion.identity);
}

private Transform SelectTarget(Transform target, Transform fallback)
{
    return target ?? fallback;
}

private void SetTargetFallback(Transform fallback)
{
    _target ??= fallback;
}

네이티브 Unity 객체가 파괴된 뒤에도 관리되는 UnityEngine.Object 래퍼는 남을 수 있다. Unity가 오버로드한 동등 비교와 암시적 Boolean은 이 분리된 래퍼를 null로 판정하지만, ?., ??, ??=는 CLR null만 검사하므로 파괴 상태를 우회한다. 현재 생명주기가 안전해 보여도 GameObject, Component, MonoBehaviour, ScriptableObject를 비롯한 Unity 객체 참조에는 이 연산자를 쓰지 않는다. 접근 직전에 target != null 또는 if (target)로 검사하고 fallback은 명시적 분기로 선택한다. object, 인터페이스, 제네릭이 Unity 객체를 감출 수 있으면 먼저 UnityEngine.Object로 복원해 검사한다. 일반 관리 객체, nullable 표기, 삼항 연산자 ?:, OnCompleted?.Invoke(item) 같은 delegate·event에는 이 제한을 적용하지 않는다. 자세한 동작은 UnityEngine.Object 공식 문서를 참고한다.

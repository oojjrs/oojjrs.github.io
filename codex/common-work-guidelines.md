# Codex Work Rules

Canonical URL: `https://oojjrs.github.io/codex/common-work-guidelines.md`

This URL is the only authoritative runtime source. Read it once at the start of each actual-work thread or subagent. Do not re-read it before every command or tool call. Reload only in a new thread or subagent, after context restoration, or when the user explicitly asks. Repository and cached copies are never runtime substitutes.

1. At the start of each request, protect every pre-existing or concurrently appearing working-tree or index change and untracked item except task-owned temporary or generated output identified under rule 8. Protection prevents unauthorized reversion, overwriting, or unrelated alteration of the user's work; it does not prohibit necessary in-scope content edits authorized by the current request or rule 5, and it does not by itself decide staging eligibility. Under a current Git-completion instruction, protected existing bytes may be staged unchanged only when pre-stage reconciliation classifies them as requested scope or related support for the carried task outcome; unrelated or unknown protected bytes remain unstaged and uncommitted. A request to change behavior or content authorizes the minimum necessary hunks even when the target file already contains protected work; preserve every other hunk. Discovering a suspected defect, conflict, invalid state, or validation failure in protected work does not by itself authorize a repair beyond the current content scope: stop before making an unauthorized change, report the problem, and wait for a content-change instruction that includes that work. Never clean, revert, overwrite, normalize, move, delete, stage, commit, or bundle unknown work outside the current task scope. If safe isolation is impossible, stop before writing and report the blocker.
2. Follow system and developer instructions, then the latest user request. Within that scope, apply this document as the highest-priority shared project guidance.
3. Apply these rules to repository, code, document, asset, Git, validation, or deployment work. Ordinary conversation, factual Q&A, translation, and rewriting do not need this workflow unless the user asks about the rules themselves.
4. Load only the references required by the task:
   - Before any game UI design, implementation, modification, or review, read and follow `https://oojjrs.github.io/codex/game-ux-guideline.md`.
   - Before creating or changing first-party application or business-layer names in games or servers, read and follow `https://oojjrs.github.io/codex/semantic-layer-naming-guideline.md`.
   - Before adding or editing first-party logs, read and follow `https://oojjrs.github.io/codex/logging-guideline.md`.
   - Before creating or editing any document or HTML file, read and follow `https://oojjrs.github.io/codex/document-writing-guideline.md`. Its text-addition approval rule, including the project-root CodexWorkMemory.md exception, takes precedence over domain-specific writing, synchronization, or publication instructions.
   - Before Unity C# product/service implementation, pre-work planning or requested step-by-step execution, read and follow `https://oojjrs.github.io/codex/practical-work-guidelines.md`. A saved plan, checklist and post-plan execution approval apply by default to Unity C# implementation of end-user products/services. Apply this workflow to reusable libraries and non-Unity work only when the user requests it. Infer applicability autonomously from the current request and existing project evidence; do not maintain project classification lists or ask routine classification questions. Other work proceeds within existing authorization.
   - Before Unity work, read and follow `https://oojjrs.github.io/codex/unity-work-guidelines.md`, including before selecting a Unity workflow skill.
   - Load and follow `https://oojjrs.github.io/codex/validation-guideline.md` once, immediately before the first validation step, only when a task changes files or external state or requests validation. When it applies, it is the controlling cross-domain authority for validation scope, execution-surface authority, oracle selection, budget, retries, and reporting. Domain workflows may add only narrower checks or stricter safety limits; they may not replace, skip, weaken, or broaden it. Reading it for a rules review does not activate validation.
5. Review, diagnosis, explanation, planning, and status requests are read-only: inspect and report without editing files, running builds or tests, starting servers or browsers, or changing external state unless the request targets that activity. 프로젝트 작업의 기록·재개에는 문서 작성 지침의 CodexWorkMemory.md 예외를 적용한다. 이 예외는 읽기 전용 작업의 메모리 갱신과 기존 작업 기록 저장 금지·$Trash 한정 규정보다 우선하며, 다른 파일 수정이나 작업 실행·승인 권한은 늘리지 않는다. For pre-work planning, the decision-recording process in `https://oojjrs.github.io/codex/practical-work-guidelines.md` authorizes minimal creation and updates of the work checklist and project planning document within the document writing limits and approval requirements to persist confirmed decisions and unresolved planning points before continuing questions; other planning activity remains read-only unless requested. For review and diagnosis, separate verified facts, inference, and unresolved uncertainty, and base causality on actual calls, references, state lifetime, or equivalent evidence rather than the first symptom or a name-only match. A change or fix request authorizes reversible local edits within its content scope; Unity C# product/service implementation and explicitly requested step-by-step work additionally require a presented plan and post-plan execution approval under rule 4. It does not by itself authorize staging or committing. When a task commit is authorized and related CodexWorkMemory.md updates exist, include them atomically in the same commit as the associated work without a separate inclusion request; do not defer those records to a separate memory-only follow-up commit. Do not create filler changes when no new record is needed; unrelated or unknown memory hunks remain excluded. Treat every explicitly requested outcome as part of completion; if one cannot be completed, report it as a remaining blocker instead of silently finishing a subset. After ordinary content work and permitted validation, leave the task's changes unstaged and uncommitted, report the scoped diff for user review, and wait for an explicit Git-completion instruction. Stage or commit only when the current request explicitly asks for that outcome; an upfront instruction or a requested push or publication authorizes the minimum scoped staging and local commit needed without a second permission. An authorized staging, commit, push, deploy, release, or publication instruction includes maintenance-document and governed version updates needed for the requested scope without a separate content-change instruction, within the document writing rules' text-addition approval scope. Git-completion authorization alone does not approve new document wording. Complete those updates before freezing and staging the final scope, preserving user-authored code, assets, and unrelated hunks. This does not authorize unrelated implementation changes, repairs, cleanup, formatting, or regeneration. If completion requires another content change outside the already authorized scope, stop and report; continue only after a content-change instruction that includes it. A later Git-completion request in the same Codex task carries the most recently reported uncommitted content scope forward as its candidate Git scope unless the latest request changes it; carrying scope forward does not itself authorize unrelated content edits or a Git operation. Immediately before staging, reconcile the current working tree, index, and untracked paths against that candidate scope and the requested outcome, classify review-time or newly appearing changes, and freeze only the reconciled scope. When a request combines content work with staging or commit, complete every requested content action first and freeze that reconciled scope immediately before staging. For every project, authorize pushes only to its dedicated repository: resolve it from the task's explicit project or repository context or its saved project checkout, then verify the Git root and remote before pushing. Treat every other repository merely opened, nested, or consulted in the same workspace as reference-only and never push to it, even if the user later asks from that wrong repository context; reject the request as targeting a non-dedicated repository. If the dedicated repository cannot be positively identified, or the candidate remote does not match it, do not push and report the ambiguity. Before a requested branch push or branch-backed publication, fetch the exact target remote and branch, then compare the local target branch with the fetched target. If the local branch is behind and has no local-only commits, fast-forward it; if both sides have commits absent from the other, rebase the local commits onto the fetched target unless the user explicitly chose a merge. Before moving or rewriting a dirty branch, recoverably preserve its index, unstaged changes, and untracked paths, restore them before continuing, and retain the preservation until restoration is verified. Treat ordinary same-repository upstream changes as concurrent project work to integrate, not a reason to create an alternate worktree or publication branch. Existing local commits on the target branch are branch history, not uncommitted staging scope, and remain part of the push after rebase unless the user explicitly requests a history change. After every branch push, read back the exact remote target, verify that it contains the pushed commit, and before claiming completion reconcile the checkout where the request began so its local target branch resolves to the verified remote tip with its preserved index, unstaged changes, and untracked paths restored. If independent local commits or an actual restore conflict prevent that reconciliation, retain the preservation and report the exact blocker; an initiating branch left behind by an isolated-worktree push is not completion. An explicitly requested merge, rebase, cherry-pick, or revert permits its normal worktree and index changes plus the minimum conflict resolution needed to complete that operation, but no unrelated repair. Push, deploy, release or publication, permanent deletion outside task-owned temporary output, forced rollback, destructive history rewrite, and paid generation require explicit current-request authorization.
6. Respect the existing project stack. For new standalone Windows automation or web work with no established stack, prefer PowerShell and .NET; do not expand a legacy or rejected stack without a task-specific reason.
7. Preserve each existing text file's encoding and line endings unless conversion is requested. New text files use UTF-8 without BOM and CRLF.
8. Keep disk I/O and context proportional to the task: use targeted searches, batch independent reads, reuse unchanged evidence, and avoid rescanning unchanged state. Apply the document-writing guideline's memory initialization, recording, provenance, freshness and retrieval policy: start with the current summary and progress, search relevant history when a request depends on prior decisions, reuse already-read unchanged content, and let Codex maintain the summary and index while preserving original records. Immediately after confirming, revising or withdrawing a user decision or making a meaningful Codex work judgment, record new decisions, reasons and uncertainties before the next dependent step or question. Before the final response, compare the request, decisions, changes, actual verification results, blockers and next steps against the relevant memory and summary; fill omissions and refresh status as needed. Also complete this check before freezing and staging an authorized task commit so related memory changes are included atomically with the work. No new meaningful information means no file edit or filler log is required, not that the omission check may be skipped. Reuse unchanged evidence and relevant sections rather than rereading the whole history or expanding validation. Memory records must identify second-resolution timezone-qualified writing time, speaker and decision owner, source thread and available source-item/worker context. Keep source event/activity/storage/import times separate, track explicit corrections and supersession, and compare current evidence instead of treating later storage or another PC's clock as a newer decision. Mark unknown times and unresolved conflicts, and date summaries by their last verified evidence. When CodexWorkMemory.md is absent, reconstruct it from the actual messages and dates/provenance of all accessible project-related active and archived user chats, covering all listing and conversation pages and confirmed prior checkout/host aliases. Record the source cutoff, scope, read coverage, unavailable history and continuation point; an empty file, a current-request-only note or a partial scan is not completed initialization. Resume explicitly unfinished initialization without rescanning completed unchanged sources, and state the limits when no earlier history is available. Put controllable temporary and intermediate files in the literal `$Trash` folder directly under the project root. For work without a project, use `$Trash` directly under the current working directory. Everything inside `$Trash` is disposable task material: Codex may create, replace, move, or delete it without separate permission. A file known to have been created solely as temporary or generated output by the current task is likewise task-owned and may be removed after use. Never move protected user or parallel work into `$Trash` unless the user asks. 프로젝트 작업의 기록·재개에는 문서 작성 지침의 CodexWorkMemory.md 예외를 적용한다. 이 예외는 읽기 전용 작업의 메모리 갱신과 기존 작업 기록 저장 금지·$Trash 한정 규정보다 우선하며, 다른 파일 수정이나 작업 실행·승인 권한은 늘리지 않는다.
9. Load only the smallest non-overlapping set of applicable workflows and follow their documented triggers and precedence. The validation guideline is not a generic parent workflow: when rule 4 activates it, it remains controlling over conflicting workflow text.
10. Do not add repository instruction files beyond a pointer to `$oojjrs-guidelines` unless the user explicitly requests an exception.
11. Write Git commit subjects and bodies in Korean unless the user explicitly requests another language. Match the user's established history: prefer a short, concrete subject naming the changed target and action (for example, `서버 기초 작업` or `HeroSquad.UserDivisionMap 제거`), usually ending in 추가, 수정, 변경, 제거, or 정리. Preserve code identifiers, paths, proper names, and version numbers as written. Do not introduce Conventional Commits prefixes such as feat:, fix:, or chore: by default. Use a body only when the subject cannot convey necessary context; describe the actual change or reason concisely in Korean. Before committing, compare the message with the staged changes and check its language and style. Do not treat recent agent-written English messages or shared Git author identity as evidence of the user's preferred style.
12. 사용자 지정 제목은 자동 제목 정리 규칙보다 우선한다. 사용자가 지정했다고 확인된 제목, 마지막으로 에이전트가 설정한 제목과 달라진 제목은 변경하지 않는다. 제목의 출처가 불분명한 경우에도 기존 제목을 보존한다. 사용자가 명시적으로 제목 변경을 요청하면 그 요청을 따른다. Write Codex task (thread) titles in Korean unless the user explicitly requests another language. At the first available opportunity in each task, assess whether the current title accurately describes the concrete task outcome. If an automatic title is non-Korean, vague, overly generic, or inconsistent with the actual work, rename it without asking for confirmation; adjust it once more if the task purpose later becomes materially clearer. Keep code identifiers, paths, and proper names in their original form when needed.

13. For repository implementation, document, asset, maintenance, or Git-completion work, check the repository-linked GitHub Projects once per task using the resolved remote. When a relevant open board is linked, use $oojjrs-github-project-board automatically unless the user opts out. This is the user's standing authorization across chats for task-scoped card and issue creation or reuse, linking issues to the board, draft-to-issue conversion, assignment to oojjrs, status and field updates, necessary body updates, and progress comments. Do not ask for separate board permission or treat these routine operations as requiring a new external-publication or Git-completion instruction; a narrow code or asset approval does not revoke this board authority. Convert a draft to an assigned issue before active work, record progress in issue comments, and mark completion only from verified results. If no board is linked, access fails, or several boards are ambiguous, report the actual limitation without creating a board or presenting existing authorization as missing user permission. Read-only questions, reviews, and diagnosis do not mutate cards unless board management is requested.
14. Do not add code comments unless the user explicitly requests them.
15. Never open a Codex side panel for any reason unless the user explicitly instructs Codex in the current request to open that side panel. This applies to files, browsers, terminals, reviews, previews, validation, playback, inspection, comparison, and completed deliverables. Otherwise, report a path or link without opening it.
16. Never use CUA (computer-use automation) or UIA (Windows UI Automation), including for read-only inspection. Do not interrupt or control the user's active desktop, browser, windows, tabs, focus, pointer, or keyboard through any other route. Use background commands, APIs, or isolated processes that leave the user's work undisturbed. If a task requires access that would interfere with the user's work, stop and report the blocker instead of asking the user to enable it.
17. Parameter default values and named arguments are prohibited by default; obtain the user's explicit approval before using either syntax in code.
18. Run every shell-based GitHub request outside the sandbox from the first attempt with `sandbox_permissions: require_escalated`, including authentication checks, `gh` reads and writes, GitHub REST/GraphQL calls, Git network operations, and GitHub downloads or installers. Never probe GitHub inside the sandbox first or treat a sandbox credential failure as a reason to reauthenticate or alter stored credentials.
19. 단일 작업은 메인이 직접 수행하고 검수한다. 병렬 분담이 필요한 독립 작업이 여러 개일 때만 현재 메인과 동일한 모델과 추론 강도의 서브에이전트에 맡긴다. 각 서브에이전트는 맡은 작업과 자체 검수를 완료하고, 메인은 작업 분배·조율·결과 취합을 담당한다. 메인의 모델과 추론 강도는 사용자가 명시적으로 요청하지 않는 한 변경하지 않는다.

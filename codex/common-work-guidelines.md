# Codex Work Rules

Canonical URL: `https://oojjrs.github.io/codex/common-work-guidelines.md`

This URL is the only authoritative runtime source. Read it once at the start of each actual-work thread or subagent. Do not re-read it before every command or tool call. Reload only in a new thread or subagent, after context restoration, or when the user explicitly asks. Repository and cached copies are never runtime substitutes.

1. At the start of each request, protect every pre-existing or concurrently appearing working-tree or index change and untracked item except task-owned temporary or generated output identified under rule 8. Protection means Codex may not edit, revert, overwrite, normalize, move, delete, or otherwise alter those bytes; it does not by itself decide staging eligibility. Under a current Git-completion instruction, protected existing bytes may be staged unchanged only when pre-stage reconciliation classifies them as requested scope or related support for the carried task outcome; unrelated or unknown protected bytes remain unstaged and uncommitted. A request to change behavior or content authorizes the minimum necessary hunks even when the target file already contains protected work; preserve every other hunk. Never clean, revert, overwrite, normalize, move, delete, stage, commit, or bundle unknown work outside the current task scope. If safe isolation is impossible, stop before writing and report the blocker.
2. Follow system and developer instructions, then the latest user request. Within that scope, apply this document as the highest-priority shared project guidance.
3. Apply the operational rules in this document to repository, code, document, asset, Git, validation, or deployment work. Ordinary conversation, factual Q&A, translation, and rewriting do not need that workflow unless the user asks about the rules themselves, but the final-answer presentation requirements in rules 10 and 11 apply to every answer.
4. Review, diagnosis, explanation, planning, and status requests are read-only: inspect and report without editing files, running builds or tests, starting servers or browsers, or changing external state unless the request targets that activity. For review and diagnosis, separate verified facts, inference, and unresolved uncertainty, and base causality on actual calls, references, state lifetime, or equivalent evidence rather than the first symptom or a name-only match. A change or fix request authorizes reversible local edits within its scope, but does not by itself authorize staging or committing. Treat every explicitly requested outcome as part of completion; if one cannot be completed, report it as a remaining blocker instead of silently finishing a subset. After ordinary content work and permitted validation, leave the task's changes unstaged and uncommitted, report the scoped diff for user review, and wait for an explicit Git-completion instruction. Stage or commit only when the current request explicitly asks for that outcome; an upfront instruction or a requested push or publication authorizes the minimum scoped staging and local commit needed without a second permission. A later Git-completion request in the same Codex task carries the most recently reported uncommitted content scope forward as its candidate Git scope unless the latest request changes it; this grants neither content-edit authority nor Git authority by itself. Immediately before staging, reconcile the current working tree, index, and untracked paths against that candidate scope and the requested outcome, classify review-time or newly appearing changes, and freeze only the reconciled scope. When a request combines content work with staging or commit, complete every requested content action first and freeze that reconciled scope immediately before staging. Before a requested branch push or branch-backed publication, fetch the exact target remote and branch, then compare the local target branch with the fetched target. If the local branch is behind and has no local-only commits, fast-forward it; if both sides have commits absent from the other, rebase the local commits onto the fetched target unless the user explicitly chose a merge. Before moving or rewriting a dirty branch, recoverably preserve its index, unstaged changes, and untracked paths, restore them before continuing, and retain the preservation until restoration is verified. Treat ordinary same-repository upstream changes as concurrent project work to integrate, not a reason to create an alternate worktree or publication branch. Existing local commits on the target branch are branch history, not uncommitted staging scope, and remain part of the push after rebase unless the user explicitly requests a history change. After every branch push, read back the exact remote target, verify that it contains the pushed commit, and before claiming completion reconcile the checkout where the request began so its local target branch resolves to the verified remote tip with its preserved index, unstaged changes, and untracked paths restored. If independent local commits or an actual restore conflict prevent that reconciliation, retain the preservation and report the exact blocker; an initiating branch left behind by an isolated-worktree push is not completion. An explicitly requested merge, rebase, cherry-pick, or revert permits its normal worktree and index changes plus the minimum conflict resolution needed to complete that operation, but no unrelated repair. Push, deploy, release or publication, permanent deletion outside task-owned temporary output, forced rollback, destructive history rewrite, and paid generation require explicit current-request authorization.
5. Respect the existing project stack. For new standalone Windows automation or web work with no established stack, prefer PowerShell and .NET; do not expand a legacy or rejected stack without a task-specific reason.
6. Preserve each existing text file's encoding and line endings unless conversion is requested. New text files use UTF-8 without BOM and CRLF.
7. Load and follow `https://oojjrs.github.io/codex/validation-guideline.md` once, immediately before the first validation step, only when a task changes files or external state or requests validation. Do not activate that workflow for unrelated read-only work. Reading the document because its rules are themselves under review is allowed and does not activate validation.
8. Keep disk I/O and context proportional to the task: use targeted searches, batch independent reads, reuse unchanged evidence, and avoid rescanning unchanged state. Put controllable temporary and intermediate files under a literal `$Trash` directory. Everything inside `$Trash` is disposable task material: Codex may create, replace, move, or delete it without separate permission. A file known to have been created solely as temporary or generated output by the current task is likewise task-owned and may be removed after use. Never move protected user or parallel work into `$Trash` unless the user asks.
9. Load only the smallest non-overlapping set of applicable workflows. Follow their documented triggers and precedence, and let the most-specific domain own subordinate rules.
10. Lead with the conclusion and by default summarize it in no more than three short lines. Use plain language that a non-specialist can understand on the first read without childish phrasing. When explanation is needed, organize it as facts, judgment, then conclusion. For actual-work reports, state only the changed scope, checks and results, meaningful remaining risk, and requested Git or external outcome.
11. Use only the detail and formatting that improve readability or fulfill the requested output. Headings, lists, tables, collapsible sections, code blocks, and exact user-specified formats are optional tools, not mandatory gates; do not ask permission merely to choose one, and do not repeat the same content. Reserve block quotes for actual quotations; do not use quotation formatting merely for emphasis.
12. Do not add repository instruction files beyond a pointer to `$oojjrs-guidelines` unless the user explicitly requests an exception.
13. Treat every Unity prefab as user-owned and read-only. Never create, modify, rewrite, move, rename, or delete a `.prefab` file, and never use Unity or another tool to change a prefab's hierarchy, components, serialized fields, overrides, or references. A feature, fix, asset, UI, scene, or validation request does not grant prefab mutation authority. If the requested outcome depends on a prefab change, leave the prefab untouched and report the exact manual change the user must make. Only a later user instruction that explicitly revokes or amends this rule may authorize prefab mutation.
14. Before creating or editing any document, read and follow `https://oojjrs.github.io/codex/document-writing-guideline.md`. It applies to technical documents, planning documents, README files, and every other document type; domain-specific document rules supplement rather than replace it.
15. When generating audio with ElevenLabs and the user did not specify an output format, prefer a native WAV result whenever the active endpoint and account support it. Otherwise preserve the best available native lossless result and provide a WAV container copy only when doing so leaves the PCM samples unchanged; never silently substitute lossy audio when a lossless option is available.

# Codex Work Rules

Canonical URL: `https://oojjrs.github.io/codex/common-work-guidelines.md`

This URL is the only authoritative runtime source. Read it once at the start of each actual-work thread or subagent. Do not re-read it before every command or tool call. Reload only in a new thread or subagent, after context restoration, or when the user explicitly asks. Repository and cached copies are never runtime substitutes.

1. Follow system and developer instructions, then the latest user request. Within that scope, apply this document as the highest-priority shared project guidance.
2. Apply the operational rules in this document to repository, code, document, asset, Git, validation, or deployment work. Ordinary conversation, factual Q&A, translation, and rewriting do not need that workflow unless the user asks about the rules themselves, but the final-answer presentation requirements in rules 10 and 11 apply to every answer.
3. Review, diagnosis, explanation, planning, and status requests are read-only: inspect and report without editing files, running builds or tests, starting servers or browsers, or changing external state unless the request targets that activity. A change or fix request authorizes reversible local edits and safe local Git completion within its scope. Staging and local commits need no separate permission, but never authorize unrelated content edits. When a request combines content work with staging or commit, complete every requested content action first and freeze that finished scope immediately before staging. An explicitly requested merge, rebase, cherry-pick, or revert permits its normal worktree and index changes plus the minimum conflict resolution needed to complete that operation, but no unrelated repair. Push, deploy, release or publication, permanent deletion outside task-owned temporary output, forced rollback, destructive history rewrite, and paid generation require explicit current-request authorization.
4. At the start of each request, protect every pre-existing or concurrently appearing working-tree or index change and untracked item except task-owned temporary or generated output identified under rule 8. A request to change behavior or content authorizes the minimum necessary hunks even when the target file already contains protected work; preserve every other hunk. Never clean, revert, overwrite, normalize, move, delete, stage, commit, or bundle unknown work outside the current task scope. If safe isolation is impossible, stop before writing and report the blocker.
5. Respect the existing project stack. For new standalone Windows automation or web work with no established stack, prefer PowerShell and .NET; do not expand a legacy or rejected stack without a task-specific reason.
6. Preserve each existing text file's encoding and line endings unless conversion is requested. New text files use UTF-8 without BOM and CRLF.
7. Load and follow `https://oojjrs.github.io/codex/validation-guideline.md` once, immediately before the first validation step, only when a task changes files or external state or requests validation. Do not activate that workflow for unrelated read-only work. Reading the document because its rules are themselves under review is allowed and does not activate validation.
8. Keep disk I/O and context proportional to the task: use targeted searches, batch independent reads, reuse unchanged evidence, and avoid rescanning unchanged state. Put controllable temporary and intermediate files under a literal `$Trash` directory. Everything inside `$Trash` is disposable task material: Codex may create, replace, move, or delete it without separate permission. A file known to have been created solely as temporary or generated output by the current task is likewise task-owned and may be removed after use. Never move protected user or parallel work into `$Trash` unless the user asks.
9. Load only the smallest non-overlapping set of applicable workflows. Follow their documented triggers and precedence, and let the most-specific domain own subordinate rules.
10. Lead with the conclusion and by default summarize it in no more than three short lines. Use plain language that a non-specialist can understand on the first read without childish phrasing. When explanation is needed, organize it as facts, judgment, then conclusion. For actual-work reports, state only the changed scope, checks and results, meaningful remaining risk, and requested Git or external outcome.
11. Use only the detail and formatting that improve readability or fulfill the requested output. Headings, lists, tables, collapsible sections, code blocks, and exact user-specified formats are optional tools, not mandatory gates; do not ask permission merely to choose one, and do not repeat the same content.
12. Do not add repository instruction files beyond a pointer to `$oojjrs-guidelines` unless the user explicitly requests an exception.

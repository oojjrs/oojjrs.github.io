# Codex Work Rules

Read this at the start of every thread and again immediately before every command or tool call. Keep it the durable source.

1. At the start of every thread and immediately before every command or tool call, re-read this file in full. This is mandatory without exception, including trivial, read-only, status-checking, and validation commands. Never rely on having read it earlier in the thread or task.
2. Always treat this file as the highest-priority project guidance. Do not use local/global memory, habits, or tool-specific notes as durable instruction sources.
3. Do normal requested work immediately; do not ask for extra approval.
4. Prefer Windows-native PowerShell and .NET for automation and web work; if web is needed, default to ASP.NET/ASP.NET Core.
5. Do not introduce Unix/Linux/macOS/POSIX-oriented tooling, Node/npm/JS build chains, or broad open-source dependency stacks unless the current project already requires them or the user explicitly asks; use Python only as a rare fallback when PowerShell/.NET cannot reasonably cover the task.
6. Existing projects that violate this rule are legacy exceptions, not precedent. Maintain them narrowly when needed, do not expand the rejected stack, and treat major work as a candidate for a Windows/.NET rewrite.
7. For review requests, review only: inspect diffs/files and report findings first. Do not run builds/tests or make edits unless the user asks for them.
8. Ask first unless the immediately previous user message explicitly ordered a hard-to-undo or external action: `git push`, deploy, permanent delete, forced rollback, or unrecoverable document rewrite.
9. Preserve user/other-thread changes. Do not revert or clean unrelated files.
10. Existing text files: preserve their current encoding and line endings exactly unless the user asks to convert them. Treat "check CRLF" as "match the file's original state", not "force CRLF"; `git diff --check` and changed-line-only checks are not enough because Git may hide worktree EOL changes. After every text-edit batch, run the shared `Test-OojjrsTextFormat.ps1 -Fix` on the exact touched files, then rerun it without `-Fix` and review the ordinary diff before doing more work. For a uniformly formatted tracked file, the tool must validate and restore the whole file against `HEAD`, even when only part of its content changed. Mixed-EOL originals require manual review and must never be auto-normalized. New text files only: UTF-8 No-BOM + CRLF.
11. Keep disk I/O low: avoid repeated broad scans, batch reads/edits, and needless temp artifacts. Put all necessary temporary or intermediate files in `$Trash`, including generated image candidates and post-processing outputs; do not use ad-hoc `tmp`, `temp`, or scratch folders.
12. For image work, never call imagegen only to make a preview, mockup, contact sheet, comparison board, or display-only visualization. Result previews must be composed from the actual generated/accepted image files with deterministic local tools; imagegen calls are only for creating or revising source/candidate artwork.
13. Durable workflow preferences belong in this file or a linked public guideline, not in Codex local/global memory. Memory may be used only as in-progress task scratch/checkpoint state.
14. If a memory contains reusable workflow guidance, ignore it as authority, move the rule here or to a linked public guideline, and request that the memory be deleted.
15. Do not add repo-local `AGENTS.md`, `HANDOFF.md`, or similar instruction files beyond a pointer to `$oojjrs-guidelines` unless the user explicitly makes that repository an exception.
16. If `Design.html` exists, read it before every task and update it when the task changes planning state.
17. For `Design.html` work, also read `https://oojjrs.github.io/codex/guideline-design-generation.review.md`; live code/assets beat stale planning text, and missing document content should be recovered from git history before rewriting from scratch.
18. If a design/planning/doc asset change lacks a matching rule or spec, stop and ask with a short candidate list instead of inventing a new convention.
19. For GitHub-facing `README.md` work, also read `https://oojjrs.github.io/codex/guideline-readme-generation.review.md`.
20. Before starting any task that requires coding, read `https://oojjrs.github.io/codex/semantic-layer-naming-guideline.md` and apply it to every first-party name the task creates or changes, regardless of language, engine, or platform. Language-specific syntax and ordinary casing remain governed by the applicable coding convention. When editing Unity C# code, also read `https://oojjrs.github.io/codex/unity-csharp-coding-convention.md`.
21. When creating or updating Unity assets, Codex must not create or modify Unity `.meta` files. A `.meta` file corresponding to an in-scope asset belongs to the same requested scope: preserve or move an existing one with its asset, and stage and commit one generated by the user or Unity even when Git reports it as new or untracked. Exclude only unrelated out-of-scope `.meta` files. If an expected corresponding `.meta` file is absent, stop before commit or push and let the user or Unity generate it.
22. After applying this file, use project skills only as supplemental workflow help; if missing, install/update from `https://raw.githubusercontent.com/oojjrs/oojjrs.github.io/refs/heads/master/codex/skills/install.ps1`; index: `https://raw.githubusercontent.com/oojjrs/oojjrs.github.io/refs/heads/master/codex/skills/index.md`.
23. To save context, do not load all project skills. Use only the smallest matching stack: `$oojjrs-project-start-work` for repository edits; `$oojjrs-project-finish-work` only when entering the finish phase after the last edit, never as a task-start preload; `$oojjrs-github-project-board` only for linked Projects; `$oojjrs-dirty-worktree-scope-split` only for mixed dirty trees; and one most-specific domain skill for Design.html, README, Unity code/assets/package/prefab, image/sprite/audio/Mines art, visual QA, Windows forensics, guideline maintenance, or skill maintenance work.
24. Public/shared oojjrs skills must use the `oojjrs-` prefix and keep `codex/skills/index.md`, `install.ps1`, `SKILL.md`, and `agents/openai.yaml` aligned.
25. If the git repository is linked 1:1 to a GitHub Project, use `$oojjrs-github-project-board` and that Project as the task board: check with `gh repo view OWNER/REPO --json projectsV2`, find/create the task card, convert a draft card to an issue when moving it to In Progress, assign issue-backed cards to `oojjrs`, update status/notes while working, use real newlines in card/issue bodies instead of literal `\n`, and report if no board/card update was possible.
26. For GitHub Project task records, keep issue bodies and card bodies focused on the task summary, scope, and completion criteria. Record ongoing user feedback, decisions, improvements, validation results, and remaining risks as issue comments; do not read or rewrite existing bodies just to append work history. Read bodies/notes only when title, linked issue number, and status are not enough to identify the task or when those bodies/notes themselves must change.
27. Stage/commit only the requested scope. Push only when explicitly requested.
28. Write feedback and documents in Korean; include relevant `git log` context when reporting work or choosing the next task.
29. When adding or changing first-party logs, also read `https://oojjrs.github.io/codex/logging-guideline.md`; classify each message before writing it and follow that document's rules for required system logs, warnings, debugging logs, UX LOG, uppercase English text, and `{expression}` identifier references.
30. When adding, moving, or publishing a public site document, also add a discoverable entry link from the site's existing home, navigation, index, or document list so a visitor can reach it by clicking from the site root; a direct URL alone does not count. Before reporting completion, verify the full click path in the rendered or deployed site, not only that the destination URL returns successfully.
31. A task-start or earlier read of `$oojjrs-project-finish-work` never satisfies a later validation, stage, commit, push, handoff, or final-report phase. After the last edit, re-read this file and then read the finish skill in a completed tool call before taking any finish action; if another edit occurs, restart the finish phase. Before every `git commit`, inspect and review `git diff --cached --name-status` and `git diff --cached --check` in a completed earlier tool call. Only after that review may a later tool call invoke `git commit`, and that commit command must first re-read this file and the finish skill and rerun `git diff --cached --check`. Never combine the first finish-phase read, unseen validation output, and the commit into one tool call.
32. Before creating a Unity UI asset or recommending its size, inspect the target project's actual Canvas size and, when applicable, its `Canvas Scaler` reference resolution (for example, FHD, QHD, or 4K). Evaluate the asset in its intended layout at that scale, and base its pixel dimensions and size recommendations on those project-specific values; never assume a generic Canvas resolution because apparent scale can differ materially between projects. If those settings cannot be verified, ask for the project-specific values instead of guessing.
33. In Unity C# code, never use the null-conditional (`?.`), null-coalescing (`??`), or null-coalescing assignment (`??=`) operators on a `UnityEngine.Object`-derived reference, including when a Unity object is hidden behind `object`, an interface, or a generic. These operators test CLR null and bypass Unity's destroyed-object state. Recover a `UnityEngine.Object`-typed reference when necessary, perform a Unity-aware check (`unityObject != null` or `if (unityObject)`) immediately before access, and choose fallbacks explicitly. This restriction does not apply to ordinary managed objects, delegates or events, nullable annotations, or the ternary operator (`?:`); follow the full rule and examples in `unity-csharp-coding-convention.md`.

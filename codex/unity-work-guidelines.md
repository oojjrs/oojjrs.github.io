# Unity Work Rules

Canonical URL: `https://oojjrs.github.io/codex/unity-work-guidelines.md`

Apply these rules to work in Unity projects and packages. Read them before selecting a Unity workflow skill.

1. Treat every Unity prefab as user-owned. Before creating, modifying, rewriting, moving, renaming, or deleting a `.prefab` file, or changing its hierarchy, components, serialized fields, overrides, or references, present the exact target prefabs, intended changes, and official Unity CLI operation to the user and obtain explicit approval for that scope. A general feature, fix, asset, UI, scene, or validation request alone does not grant prefab mutation authority. Prepare the proposed operation for review without mutating prefabs; approval must precede execution. If the user has already explicitly approved that same scope and CLI operation in the current task, do not ask again. Execute approved changes only through the [official Unity CLI](https://docs.unity.com/en-us/unity-cli), using the supported Editor integration for the project version; never directly edit prefab YAML or bypass the CLI with another mutation tool. If the required CLI capability is unavailable or the scope changes, leave unapproved prefabs untouched and report the blocker or obtain approval for the revised operation. After execution, inspect the resulting prefab diff and report the changes and validation evidence.
2. Before writing or editing Unity C# code, follow `https://oojjrs.github.io/codex/unity-csharp-coding-convention.md`. That document governs code conventions; these rules govern work in the Unity environment.
3. Keep application and business logic free of routine defensive null checks. Guarantee required references are non-null upstream through construction, initialization, ownership, and call contracts. Concentrate necessary null handling in library-level code and boundaries that directly call Unity or other external APIs, or where null is an intentional, documented part of the contract. A library location or Unity API call alone does not justify a check: confirm that null can actually occur and must be handled there. Use existing safety abstractions and extension functions such as `Safety` according to their actual contracts so project logic can rely on the guarantees they provide; do not duplicate their checks at call sites. If a required non-null guarantee is broken, fix its source instead of hiding it with a null guard, early return, skipped operation, fallback, or null-conditional/coalescing operator. Hypothetical nullability is not enough to add defensive code. The C# convention's Unity object validity and operator rules govern how an allowed check is written and do not authorize routine null checks in project logic.

# Unity Work Rules

Canonical URL: `https://oojjrs.github.io/codex/unity-work-guidelines.md`

Apply these rules to work in Unity projects and packages. Read them before selecting a Unity workflow skill.

1. Mutate Unity-serialized project assets only through the [official Unity CLI](https://docs.unity.com/en-us/unity-cli) and its supported Unity Editor integration. This includes `.unity`, `.prefab`, `.asset`, `.anim`, `.controller`, `.overrideController`, importer settings, serialized references, and Unity-side creation, move, rename, deletion, import, or reimport operations. Never hand-edit their YAML or bypass the CLI with another mutation tool. Read-only text search, GUID tracing, and Git diff review remain allowed. Source art and audio may be authored outside Unity, but their project import and serialized configuration must go through the CLI. Ordinary C# may be authored directly with text tools. When a task only creates or edits ordinary `.cs` source, use normal text and filesystem tools; do not search for, install, launch, or invoke the Unity CLI or Editor for that task, including script import, `.meta` generation, compilation, or validation. Select the CLI only when the requested work separately requires a Unity-serialized asset mutation, Unity-side asset move, rename, import or reimport, or Editor configuration. If the compatible CLI, Editor, Pipeline package, or required command is unavailable, stop that mutation phase instead of falling back to raw files.
2. Never hand-create, hand-edit, or fabricate a Unity `.meta` file or GUID. Let Unity generate or update metadata through a CLI-driven Editor import, `AssetDatabase` operation, or project open/save. For a new ordinary C# file created during code-only work, leave `.meta` generation to the next normal Unity project open or import instead of invoking the CLI solely for metadata. Use Unity asset APIs for moves and renames so existing GUIDs remain stable. Include every Unity-generated in-scope `.meta` with its asset, inspect unexpected GUID changes before commit, and stop if an expected companion is still absent after an official import/save path that the requested work actually required.
3. Treat every Unity prefab as user-owned. Before creating, modifying, rewriting, moving, renaming, or deleting a `.prefab` file, or changing its hierarchy, components, serialized fields, overrides, or references, present the exact target prefabs, intended changes, and official Unity CLI operation to the user and obtain explicit approval for that scope. A general feature, fix, asset, UI, scene, animation, or validation request alone does not grant prefab mutation authority. Prepare the proposed operation for review without mutating prefabs; approval must precede execution. If the user has already explicitly approved that same scope and CLI operation in the current task, do not ask again. If the required CLI capability is unavailable or the scope changes, leave unapproved prefabs untouched and report the blocker or obtain approval for the revised operation. After execution, inspect the resulting prefab diff and report the changes and validation evidence.
4. Before creating a UI image or recommending its dimensions, read the project's planning document for the current FHD, QHD, or 4K reference resolution. If it is not declared, use FHD (1920x1080) as the default design baseline. Read the actual Canvas and `Canvas Scaler` through the official Unity CLI when available, and report a mismatch instead of silently replacing the planning baseline.
5. Before writing or editing Unity C# code, follow `https://oojjrs.github.io/codex/unity-csharp-coding-convention.md`. That document governs code conventions; these rules govern work in the Unity environment.
6. Keep application and business logic free of routine defensive null checks. Guarantee required references are non-null upstream through construction, initialization, ownership, and call contracts. Concentrate necessary null handling in library-level code and boundaries that directly call Unity or other external APIs, or where null is an intentional, documented part of the contract. A library location or Unity API call alone does not justify a check: confirm that null can actually occur and must be handled there. Use existing safety abstractions and extension functions such as `Safety` according to their actual contracts so project logic can rely on the guarantees they provide; do not duplicate their checks at call sites. If a required non-null guarantee is broken, fix its source instead of hiding it with a null guard, early return, skipped operation, fallback, or null-conditional/coalescing operator. Hypothetical nullability is not enough to add defensive code. The C# convention's Unity object validity and operator rules govern how an allowed check is written and do not authorize routine null checks in project logic.
7. Keep project UI strictly passive and callback-driven. Application and business code owns every decision, performs operations, updates Hub/model state, and publishes result or state-change notifications. UI only reacts to externally changed state and reflects the already determined results in its presentation.
   - UI code must not implement operations, determine what should happen, orchestrate application or game flows, or decide whether or when a UI is needed. Keep all such decisions outside UI. Opening, closing, and refreshing only reflect externally determined state through the established callbacks; UI handlers read that state and apply the corresponding presentation without making independent decisions or creating new state to drive the application.
   - A button callback only calls one application or business-layer processing function to delegate the received input, then returns. The callback must not perform condition or eligibility checks, branch on application state, calculate values, mutate state, control UI, or sequence multiple operations. Put all decisions, state lookup, validation, and processing in the delegated function outside UI; moving that work into another UI helper does not satisfy this rule.
   - Every UI subscribes and unsubscribes exclusively through the project's existing `Listener` abstraction and `Updater` lifecycle. UI code must never register or remove callback events directly with `+=`, `-=`, `AddListener`, `RemoveListener`, or equivalent event/delegate registration APIs. Actual event wiring belongs inside the established `Listener` implementation; add a missing notification binding there instead of subscribing directly in UI code. Preserve subscription lifecycle ownership and the existing initial refresh. A refresh deferred by a callback flag is still callback-driven; do not replace this with independent state polling. Keep the necessary UI observers active within an existing category so initially hidden descendants can open in response to notifications.
   - Never directly invoke a UI component's public methods, pass initialization or display parameters to it, or inject its display data through external setters. This prohibition applies to application code, business code, other UI components, and indirect calls through Hub helpers or wrappers. UI reads data from the established Hub/model state and lookup mechanisms; do not disguise an imperative UI call as a callback or introduce a UI-parameter API.
   - The sole direct-opening exception is the project's established top-level category UI roots, such as Title, Ingame, Lobby, or Common, through the existing bootstrap/category entry path needed to establish their initial Hub subscriptions. The category set is fixed when the project is created: do not add or remove exception roots, promote a child panel to a root, or extend the exception to dialogs, popups, or other descendants. This exception permits root opening only; it does not permit public UI method calls or UI parameters.
   - Existing direct calls or non-root panel-opening helpers are not precedent for another exception. Follow this architecture for new or changed behavior; report out-of-scope violations without silently rewriting unrelated UI.
